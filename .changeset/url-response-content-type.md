Add a `responseContentType` option to `url()` that overrides the `Content-Type` of the response, so a PDF stored as `application/octet-stream` can be previewed inline instead of downloaded. It is bound into the signed URL by S3 and every S3-compatible adapter (on either client engine), `files-sdk/bun-s3`, `files-sdk/gcs`, `files-sdk/firebase-storage`, `files-sdk/azure` with a signer, and `files-sdk/r2` over HTTP or in hybrid mode, and, like `responseContentDisposition`, it forces signing when a `publicBaseUrl` is configured. The new `capabilities.signedUrl.contentType` reports whether an instance can bind it; where it can't, `url()` throws `Unsupported` before the adapter is called, and a value that isn't exactly one media type, written in ASCII, throws `Invalid`. In `files-sdk/api`, `authorize` can return `responseContentType` to override the type of `download` and `url`: downloads redirect with it bound where the adapter supports it and are proxied with that `Content-Type` otherwise (the proxy's sandbox policy is decided on the type it sends), and the `url` operation fails with `Unsupported` on adapters that can't bind it. Browsers can't request a content type. The field is optional on `SignedUrlCapability`, so a plugin `capabilities` hook that builds its own `signedUrl` object keeps compiling; leaving it out reads as `false`.
